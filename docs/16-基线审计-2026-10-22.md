# 16 — 基线审计：镜像里到底有没有别人的文件（2026-10-22）

> **来源署名**：本机当前 boot 链与 `vendor` / `odm` 分区来自 **施（QQ 2233209163）** 制作的 **澎湃 OS（HyperOS）移植包**。
> 本仓库**不含该包的任何文件**，只在本机作为底包使用。感谢他救活这台机器。
> 下文表格里的「施 的包」= 指这个移植包；「官方 BAK」= ZTE 官方工具箱（作者 **酷安 @某贼**）导出的全分区备份。

用户要求核实「确保没用别人的东西」。这里把两件事分开审计：
**① 我们编出来的三个镜像里有什么**；**② 手机上现在跑的分区分别来自哪里**。

## 一、编出来的镜像里有什么

| 内容 | 来源 | 核验方法 | 结论 |
|---|---|---|---|
| 8 个 IMS APK（ims / QtiTelephony / qcrilmsgtunnel / QtiTelephonyService / ImsRcsService / ImsDataChannelService / imssettings / uceShimService） | **ZTE 官方 BAK** 的 `system_ext` | 比 `classes*.dex` 的 md5：8 个全部 `SAME-DEX`（整包 md5 不同只因我们重签 + 删了 manifest 里的自指向 overlay 节点） | ✅ 官方 |
| 15 个 IMS jar（`vendor.qti.ims.*`、`com.qualcomm.qti.uceservice-*`、`qcrilhook`） | ZTE 官方 BAK | 逐个 md5 对比，15/15 相同 | ✅ 官方 |
| 3 个指纹 APK（`FingerprintSensorUi_ZTE` / `FingerprintService_ZTE` / `FingerPrintSettings_ZTE`） | ZTE 官方 BAK 的 `system` | 逐个 md5 对比，3/3 相同 | ✅ 官方 |
| 3 个 privapp 白名单 xml | ZTE 官方 BAK | 从 `~/stock_sys.img` 的 `/system/etc/permissions` 抽出 | ✅ 官方 |
| `prebuilts/Image`（内核） | 原为 施 的包的 6.6.143（md5 `a1e98cb7…`） | 已替换为 BAK 官方 `boot_a.img` 里抽出的 6.6.92（md5 `3cacb265…`，36,596,224 B） | ✅ 已修正 |

**结论：三个镜像里没有任何 别人的文件。** 之前唯一的例外是设备树里躺着的 `prebuilts/Image`（施 的包里的内核），
它不会被塞进 system（我们也不刷 boot），但已按用户要求换成官方内核。

## 二、手机上现在跑的分区来自哪里

这是**审计暴露出来的真问题**：手机上并非「官方底包 + LOS 三镜像」，而是一个混搭状态。

| 分区 | 设备当前 md5 | 官方 BAK | 施 的包 | 判定 |
|---|---|---|---|---|
| `boot_a` | `da47c867…` | `da47c867…` | `d8ffd1a7…` | 官方 ✅ |
| `init_boot_a` | `aa25b4e0…` | `e252ad6f…` | `aa25b4e0…` | **施 的包** ❌ |
| `vendor_boot_a` | `e4207ee9…` | `ccea4080…` | `e4207ee9…` | **施 的包** ❌ |
| `dtbo_a` | `a9f4704a…` | `c8f2120d…` | `a9f4704a…` | **施 的包** ❌ |
| `vbmeta_a` | `a90fd994…` | `c922b921…` | `a90fd994…` | **施 的包** ❌ |
| `vbmeta_system_a` | `6ceed0bb…` | `782bc0c3…` | `6ceed0bb…` | **施 的包** ❌ |
| `vendor_a` | `a4d78543…` | `2e3b10dc…` | `a4d78543…` | **施 的包** ❌ |
| `odm_a` | `fe24f2cd…` | `8b8d5072…` | (施 的包 super) | **施 的包** ❌ |
| `vendor_dlkm_a` | `5f383dec…` | `5f383dec…` | — | 官方 ✅ |
| `system_dlkm_a` | `d744b22b…` | `d744b22b…` | — | 官方 ✅ |
| `system_a` / `system_ext_a` / `product_a` | — | — | — | LineageOS 自编 ✅ |

### 为什么会变成这样

1. 早期实验把 a 槽搞成 unbootable，最后是**用 施 的包整包 EDL 恢复**才救活手机 → 那一刻全机分区都变成 施 的包 的。
2. 之后为了拿回官方内核，只补刷了 `boot_a`（官方 6.6.92）。
3. 再往后所有迭代都只写 `system` / `system_ext` / `product`，**再没碰过其他分区**。

所以「官方底包」这个说法只对 `boot` 成立，其余启动链路是施 的包里的。文档里那句话是不准确的，已在此更正。

### 为什么当时不一次性刷回官方

`vbmeta_system` 有回滚保护：官方 BAK 的 rollback index 是 `1772323200`，
而设备已经被 施 的包抬高到 `1782864000`。刷低索引会被 bootloader 直接拒绝引导。
因此 `vbmeta` / `vbmeta_system` 只能保留 施 的包那一份（它是移植者用 ZTE 原厂密钥重签的，签名链本身是真的）。

## 三、要把手机也变成「全官方」，需要做什么

分两种范围：

### 范围 A（推荐，风险低）— 只把不影响 vbmeta 链的分区换回官方

```
init_boot_a      官方 e252ad6f…        （A16 的 first-stage init）
dtbo_a           官方 c8f2120d…
vendor_a         官方 2e3b10dc…        （2.68 GB，10 个 extent，需要多段 EDL 写入）
odm_a            官方 8b8d5072…
vendor_boot_a    官方 + 打 fstab avb 补丁（必须，否则 LOS 起不来）
```

- `vbmeta` / `vbmeta_system` 保持 施 的包那一版（受回滚索引限制）。
- 风险：`vendor` 换成官方后，`vendor_dlkm`（本来就是官方）与它同批，一致性反而更好。
- 回滚：`porting\vendor_backup\vendor_device_now.img`（md5 `a4d78543…`）+ 施 的包整包。

### 范围 B（不推荐）— 连 vbmeta 也换官方

需要先想办法清除 RPMB 里的回滚计数，这一步不可逆、且没有公开手段。不建议。

### 需要先补的工具

`make_edl_los_xml.py` 目前只按**单 extent** 计算起始扇区，`vendor_a` 是 10 段、
`odm_a` 是 3 段，直接写会写错位置。要支持多段写入（每个 extent 一条 `<program>`，
并按文件内偏移分段），这是范围 A 的前置工作。

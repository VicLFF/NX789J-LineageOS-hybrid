# 屏下指纹：阶段性结论（2026-10-22）

## 一句话

**system 侧能做的全部做完了，卡点确认在 vendor 层（内核 THP 驱动 ↔ `libgdix_tsa.so` 的帧校验），system / system_ext / product 三个分区改不动。**

---

## 一、现在已经完全打通的环节（这些以前都不通）

| 环节 | 状态 | 证据 |
|---|---|---|
| SystemUI → ZTE 服务（原厂 SystemUI_MFV 的那一步） | ✅ 已用自建桥接 App 打通 | `FP_UN_UdfpsMessageService: sendMessageInfo msg: 6 ... state: INITIALIZED` |
| ZTE 状态机 IDLE → INITIALIZED | ✅ | `FP_UN_FingerprintStateMachine: updateTpActionDownState state: INITIALIZED` |
| 屏下高亮（HBM） | ✅ | `[MSM_LCD] set [lcd_hbm, 1]!`，屏幕真的变亮 |
| 高亮圈 + 涟漪动画 | ✅ | `setHighLightWindowVisible visible: true`、`authAnimal X:240,Y:1863`、`drawBitmap currentIndex:0..5` |
| 手指按下 → 通知 HAL | ✅ | `tpKeyEventActionDown`、`onEnrollFingerDown` |
| 触摸采样率 | ✅ 由 1 提到 4，帧错误从 116 次降到接近 0（丢帧问题解决） | `/proc/touchscreen/tp_report_rate = 4` |

## 二、卡死点

手指按上去后，每一帧图像都被 TSA 判为无效：

```
E [gdix_tsa][ParseFramedata]: uwFrameIndex error, start:63, end:64
E [gdix_tsa][TsaProcessingFrame]: Framedata process fail...
E [gdix_tsa][UpdateFrameMissingFlag]: Missing frame, curFrameIdx(64), lastFrameIdx(62)
```

**从重启后的第一帧（start:63）就错，之后 100% 每帧都错，且 `start` 与 `end` 永远差 1。**

### 已排除的原因

| 假设 | 结论 |
|---|---|
| 显示刷新率 144Hz 导致丢帧 | ❌ 否。强制 60Hz 后同样 116 次错误 |
| 触摸采样率太低 | ✅ 这个是原因之一，已修（1→4） |
| 帧计数漂移（HAL 先吃掉一帧） | ❌ 否。重启 `odm_tsc` 让计数归零后，第一帧仍然差 1 |
| 内核驱动读不到帧 | ❌ 否。按压时 `dmesg` 零条 THP 报错，帧确实送出来了 |
| 校准数据丢失 | ❌ 否。刷回施 的澎湃 OS 包后指纹可正常录入 |
| 高亮没亮 / 状态机没起来 | ❌ 否。两项都已验证生效 |

### 结论

`libgdix_tsa.so` 对帧头做校验（`LibMemSumU8(hdr,12)` 与 `hdr[0xc]` 的两个字段比对），
而 zte THP 驱动给出的帧里这两个字段**恒定相差 1**。
这是**驱动与 TSA 库之间的帧格式/握手约定不一致**，两者都在 vendor 分区。

## 三、为什么不能从 system 侧修

- 帧的解析方 `libgdix_tsa.so` 在 `/vendor/lib64/`
- 帧的产生方是内核驱动 `/dev/thp`（vendor_boot 里的 zte 触摸模块）
- 指纹 HAL `vendor.zte.fingerprint.ztecmdaidl-service` 也在 `/vendor/bin/hw/`

三者全在 vendor 分区，而我们是 **hybrid 移植**：只替换 system / system_ext / product，
vendor / odm / vendor_dlkm / system_dlkm 全部保留官方原样。

## 四、还剩的最后一条路（风险高、不确定）

**给 vendor 分区打补丁**：我们已经有 EDL 写 super 内任意逻辑分区的完整工具链
（`porting/edl_flash.ps1` + `make_edl_los_xml.py` + `patch_super.py`），技术上可以把
改过的 `libgdix_tsa.so` 写进 `vendor_a`。

但：

1. 需要反汇编定位校验分支并改跳转，改错就是黑屏/指纹彻底失效；
2. 即使绕过校验，如果帧数据本身有问题，录入拿到的仍是垃圾图；
3. avb 已关（`veritymode=eio`），改 vendor 不会被拒，但也失去了保护；
4. 一旦刷坏 vendor，只能靠 EDL 全量恢复（我们已验证可用，53 秒）。

**建议**：先不做。等后续拿到与 6.6.92 内核配套的 ZTE 触摸驱动源码、或
RedMagicOS 的 vendor 侧差异配置后再说。

## 四之补充：vendor 侧补丁实验（已做，结论为否定，已完全回滚）

在用户要求「可随时还原」的前提下，做了一次**零写入**的验证实验：

1. 反汇编 `libgdix_tsa.so` 的 `ParseFramedata`（文件偏移 0x7c544）：
   ```
   7c5ac  mov  w1, #0xc
   7c5b0  ldrh w23, [x20, #0xc]      ; 帧头 offset 0xc 的校验和
   7c5b4  bl   LibMemSumU8           ; 前 12 字节求校验和
   7c5b8  cmp  w23, w0, uxth
   7c5bc  b.ne 0x7c61c               ; 不相等 → 整帧丢弃（打 uwFrameIndex error）
   ```
2. 把 `7c5bc` 的 `b.ne`（`01 03 00 54`）改成 `nop`（`1f 20 03 d5`），
   用 **bind mount** 覆盖 `/vendor/lib64/libgdix_tsa.so`（分区未写入，重启即失效）。
3. 结果：
   - 帧校验不再报错，但指纹**仍然录不进去**；
   - 更严重的是**整块触摸失灵**（划屏幕无反应）。

**结论**：`ParseFramedata` 解析的帧里同时承载触摸数据，绕过校验等于让垃圾数据进入触摸处理。
也就是说那条校验**不是误报，数据本身确实是坏的**。此路不通，已 `umount` 回滚并做 EDL 硬复位，
设备完全恢复（`/vendor/lib64/libgdix_tsa.so` md5 回到原版 `7b9699f3c2b09a9507ca05965c8c6da5`，
`mount | grep libgdix_tsa` = 0，功能抽查全部正常）。

**副作用经验**：连续 `pkill odm_tsc` 会把触摸芯片 ISP 留在坏状态（`Failed to prepare ISP, exit update:-50`），
必须靠 EDL 硬复位（`fh_loader --reset`）才能恢复。

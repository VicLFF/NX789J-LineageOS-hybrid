## 二、从施 的澎湃 OS 包挖到的硬信息

### 1. 音频 HAL 二进制完全相同（决定性）

| 文件 | 我们底包（ZTE 官方） | 早期参考固件 |
|---|---|---|
| `lib64/hw/libaudiocorehal.qti.so` | md5 `1820294f57c575336e4e745e6132903b`（1,444,440 B） | **同一个 md5** |

另外这些也全部 md5 相同：
`audio_module_config_primary.xml`、`sku_sun/audio_policy_configuration.xml`、`audio_policy_configuration.xml`。

→ 结论：**「通话无声」不是 vendor 侧差异**，因为两边 vendor 是同一份东西（那个施 的澎湃 OS 包其实也是刷在 ZTE 官方 vendor 上，只改了 `ro.vendor.build.fingerprint` 之类来骗 Play Integrity）。差异只能在 system 侧。

### 2. 通话参数确实到达 HAL，但 HAL 没启动语音流

拨 100010 时的完整链路日志（本次新抓）：

```
D/AudioController(3710): setParameters with: vsid=297816064;call_state=2;call_type=NR5G;crs_call=false
D/DeviceHalAidl(1720): [default]  setParameters: parameters: "call_state=2;call_type=NR5G;crs_call=false;vsid=297816064"
D/DeviceHalAidl(1720): [usb]      setParameters: ...
D/DeviceHalAidl(1720): [r_submix] setParameters: ...
D/DeviceHalAidl(1720): [bluetooth] setParameters: ...
```

- 参数**确实**从 `com.qualcomm.qti.telephonyservice` 发出，并且被 AudioFlinger 转发给**全部 4 个 HAL device 实例**。
- 但 HAL 侧随后**没有** `Telephony: INACTIVE -> ACTIVE`、也**没有** `startCall`，也就是说 `call_state=2`（ACTIVE）没被状态机接受。
- HAL 源码里的门控（`hardware/qcom-caf/sm8750/audio/primary-hal/hal/core/Telephony.cpp`）：

```cpp
// reconfigure() 末尾
if (isAnyCallActive() ||
   ((mAudioMode == AudioMode::IN_CALL) && mIsVoiceStarted)) {
   updateCalls();
}
// isAnyCallActive(): 只有 session.current_ == ACTIVE 才返回 true
```

→ 这是**死锁式门控**：只有「当前已是 ACTIVE」才处理「变成 ACTIVE」。正常能出声的路径是 `updateDevices()` 里的特例把它先撑起来：

```cpp
if (!isAnyCallActive()) {
    if (mAudioMode == AudioMode::IN_CALL && (mPalHandle == nullptr || mSetUpdates.mIsCrsCall)) {
        mIsVoiceStarted = true;
        updateCalls();
        return;
    }
}
```

我们这边这条路走过（日志有 `updateCalls ... in state IN_ACTIVE`），但 `call_state=2` 到达之后没有再触发一次 `updateCalls()`。**下一步要做的是：确认 `mAudioMode` 在参数到达时是否已经是 `IN_CALL`，以及 `mIsVoiceStarted` 是否被清掉。**

### 3. qspa：一个已知的「system 侧缺失」

施 的澎湃 OS 包的 `system_ext` 里有两个我们完全没有的文件：

```
/system_ext/etc/init/qspa_system.rc
    import /system_ext/etc/qspa/qspa_${ro.boot.vendor.qspa:-default}.rc

/system_ext/etc/qspa/qspa_default.rc
    on init
        setprop ro.boot.vendor.qspa.modem "enabled"
        setprop ro.boot.vendor.qspa.nav "enabled"
```

我们设备上 `ro.boot.vendor.qspa.*` 全是 `0`（只有 `ro.boot.vendor.qspa=true`），因为我当初把这 5 个 ZTE IMS APK 里「必须 qspa.modem=enabled」的 overlay 节点删掉了绕过。

我已确认 `/vendor/etc/qspa/` 里只有 `nsp_disabled.rc`，modem/nav/audio 对应的 rc **都不存在**，所以补上这两个 rc 只会设两个没人消费的属性，实质作用≈0，本轮**没有**加（避免引入未知副作用）。若后面发现哪个服务在等这两个属性，随时可以加。

### 4. 施 的澎湃 OS 包的 IMS APK 不能直接搬

| | 施 的澎湃 OS 包（A17） | 我们（ZTE 官方 A16） |
|---|---|---|
| `ims.apk` | md5 `83747d2c…`，`minSdkVersion=37` | md5 `76338f23…`，`minSdkVersion=36` |
| `QtiTelephony.apk` | `ac6f4593…` | `eadfe1ec…` |
| `QtiTelephonyService` / `ImsRcsService` | **包内根本没有** | 有 |

→ 参考固件连 `QtiTelephonyService`（发 `call_state/call_type` 的那个）都没有，说明它用的是私有 telephony 栈，无法照搬。

| 3 | 整机重启 + 亮度拉满（`screen_brightness_mode=0`、`screen_brightness=255`） | 无反应 |
| 4 | 上面两项改回 `false`，重启 HAL（新 pid 7942） | 无反应 |

### 精确断点

每次按手指，HAL 的顺序都固定是：

```
I/FingerprintVirtualHalSession: ZtecmdDaemon(Session):onUiReady
I/FingerprintVirtualHal:        onUiReadyImpl
I/FingerprintVirtualHalSession: ZtecmdDaemon(Session):Session::enterIdling
```

即 **收到「UI 已就绪」→ 直接进入 idle，从没进入采图态**。

同时 `odm_tsc`（TSA 用户态 pid 1777）每帧都失败：

```
E/[gdix_tsa][ParseFramedata]: uwFrameIndex error, start:3944, end:3945
E/[gdix_tsa][TsaProcessingFrame]:  Framedata process fail...
E/[gdix_tsa][UpdateFrameMissingFlag]: frameidxcheck - Missing frame, curFrameIdx(3945), lastFrameIdx(3943)
```

关键补充：`dmesg -C` 清空后再按，**按压期间内核零 THP 日志** → HAL 根本没用 `goodix_thp` 采图通道，
TSA 解析的是触摸数据而不是指纹图，所以帧号对不上。之前「出帧」的现象其实是**触摸帧**，不是指纹图。

已排除：指纹几何（官方 608/2024/94 已编进 framework-res）、`uinput-goodix.idc/.kl`（已进 `/system/usr/`）、
触控固件（`/data/vendor/touchscreen/fw/` 里 `goodix_config.cfg`/`goodix_firmware.bin`/`thp_cfg_9916.bin` 都在）、
亮度/HBM（`UdfpsDisplayMode` 只打过 `disable | onDisabled is null`，从未 enable）、HAL 存活与绑定（`HAL deaths 0`，AIDL v4 正常注册）。

→ **不是配置能解决的，需要一条「正常工作时的同类日志」做对照。**

### EDL 刷机工具（因你要求少用 fastboot）

| 文件 | 作用 |
|---|---|
| `porting\edl_flash.ps1` | 全自动 EDL 定点刷写：查工具 → 查镜像 → 从手机现拉 LP 分区表 → 生成 firehose XML → Sahara → configure → `fh_loader` 写三个逻辑分区 → reset |
| `porting\sparse2raw.py` | 纯 Python 把 sparse `.simg` 转回 raw（EDL 只能写 raw） |

`-Check` 实测全绿：

```
[OK] QSaharaServer.exe / qcedlcmdhelper.exe / fh_loader.exe / firehose.elf
[OK] system.img 594,968,576 / system_ext.img 252,579,840 / product.img 327,704,576
[OK] 已从设备现拉 LP 表（524288 字节）
  system_a     -> abs_start_sector=216584  sectors=145256  fits=True
  system_ext_a -> abs_start_sector=1898760 sectors=61665   fits=True
  product_a    -> abs_start_sector=9480    sectors=80006   fits=True
```

**注意**：分区容量是上次 fastboot resize 的结果（`system_a` 现在正好等于镜像大小）。
以后编出的镜像若变大，EDL 会报「比容量大」，那时需要先用 fastbootd resize 一次。

用法：

```powershell

powershell -ExecutionPolicy Bypass -File porting\edl_flash.ps1 -Check

# 真正刷（手机关机 → 音量+ 与 音量- 同时按住 → 插 USB，进 9008）

```
